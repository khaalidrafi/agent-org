#+title: agent-org — Org-native ACP client for Emacs
#+author: Khalid

* What is this?

~agent-org~ is a lightweight, Org-native chat UI for coding agents that
speak [[https://agentclientprotocol.com/][ACP]] (Agent Client Protocol).  Unlike ~agent-shell~, it runs no hidden
comint/terminal buffer: it talks to the ~acp~ package directly and
renders the conversation natively as an Org document.

All status, progress and error feedback appears in the chat buffer's
own *header line* (the top bar, as used by ~gptel~ and ~agent-shell~) — never
as system messages in the document body.  The body is a conversation in
/exchanges/: ONE heading per prompt/response pair, and the heading's text /is/
the prompt (~* Refactor the auth module~).  The answer sits under it inside an
Org quote block, attributed to the model that wrote it by a
~#+ATTR_TEXINFO: :author~ line, so the pair reads as /you asked this — that
model answered/ with nothing else to parse.  Tool calls follow the quote as one
~  - KEYWORD title~ item per call in an open ~:tool:~ drawer (its state written
as ~TODO~/~ONGOING~/~COMPLETE~/~FAILED~), with what each call printed as that
item's own body, and extended thinking in a folded ~:thinking:~ drawer — the
text of a reply converted from the agent's Markdown into Org markup on the way
in (see [[*What the agent wrote becomes Org]]) — plus one auto-managed
metadata block at the very top (see
[[#session-metadata][Session metadata]]) — and, by default, that whole body is mirrored to one
Org file per session, so a chat leaves you a document rather than a
buffer you had to remember to save (see [[#transcript-file][Transcript file]]).

Each exchange also records how long the agent took to answer: a
=:RESPONSE:= property (exact seconds) and a canonical Org =CLOCK:= range
sit directly under its heading, filed in a =:LOGBOOK:= drawer, so
~org-clock-collect~ and the agenda's clocktable can total response time
across a transcript.  The range is opened with its start stamp when the
prompt goes out — so a turn in flight already has a clock line, whose end
and duration are written into that same line when the answer lands — and
that /open/ line still cannot occupy Org's one global running-clock slot:
the package never calls ~org-clock-in~, never touches Org's running-clock
state, and a resumed session's restored exchanges carry no clock rather
than a fabricated one (see CONVENTIONS.md §22).  And because
Org's own clock tools round every sub-minute answer to ~0:00~, the chat
shows the seconds itself: each heading ends with its clocked total, and the
top-level exchange with the sum of its parts, ~0:00:45~ rather than ~0:00~
(see [[*Clocked seconds in the headings]]).

* Prerequisites

- Emacs 29.1+ (Org 9.0+ built in)
- The ~acp~ package (e.g. from NonGNU ELPA)
- An ACP agent binary on ~exec-path~: ~slave-acp~ (slave-agent, this
  fork's own agent --- a standalone stdio server, not a CLI subcommand),
  ~qoder --acp~ (1.1.58 tested),
  ~goose acp~ (1.50+ tested), ~opencode acp~ (1.18.29 tested) or
  ~mcode acp~ (MiniMax Code 0.4.5); plus seven wired from ~agent-shell~
  or the harness roster but not yet run against a live agent here —
  ~copilot --acp~ (GitHub
  Copilot CLI, whose ACP server is in public preview), ~agent acp~ (Cursor;
  the CLI binary is ~agent~, not ~cursor~), ~codebuddy --acp~ (CodeBuddy)
  and ~cline --acp~ (Cline); then the three the agent-team-ci harness
  image bakes and this package now covers: ~omp acp~ (OMP / oh-my-pi,
  native ACP per omp.sh/docs/acp), ~pi-acp~ (Pi --- pi itself has no ACP
  server, so this is the community adapter ~npm install -g pi-acp~, which
  spawns ~pi --mode rpc~; it implements no client filesystem or terminal
  delegation and does not forward MCP servers to pi), and
  ~dsh --profile acp~ (DeepSeek Harness, where ACP is a profile rather
  than a flag; its automation surface omits ~session/load~, so a DSH chat
  opens fresh instead of replaying history).  One more is wired but not
  baked in the harness image yet: ~gemini --acp~ (Gemini CLI --- the flag is
  spelled out in its own developer guide, geminicli.com/docs/cli/acp-mode).
  Its documented methods include ~loadSession~ and it proxies the filesystem
  through the client, but its model moves through ~unstable_setSessionModel~
  rather than a ~model~ config option, so no model is pinned; open a Gemini
  chat after ~npm install -g @google/gemini-cli~.  And ~devin acp~ (Devin,
  CognitionAI/devin-cli — the same subcommand Zed, JetBrains and Xcode
  spawn; its ACP server reads ~WINDSURF_API_KEY~ from the environment when
  set, else the credentials stored by ~devin auth login~).
  slave-agent keeps its keys in a ~.env~ inside its state dir and its model in
  ~config.yaml~, both read by the adapter itself, so Emacs exports nothing for
  it; set ~SLAVE_HOME~ in the environment Emacs was started with to bind a
  specific profile's state dir.
  Qoder reads its credential from ~QODER_PERSONAL_ACCESS_TOKEN~ in the
  environment Emacs was started with, so export it before launching Emacs or
  the daemon.  OpenCode, MiniMax Code, Copilot, CodeBuddy, Cline, OMP and Pi
  keep their own credential stores, so ~opencode auth login~ / ~mcode login~ /
  a signed-in
  ~copilot~, ~codebuddy~ or ~cline~ once is enough, ~omp~ takes
  ~/login <provider>~ and pi reads its own config; no environment variable is
  required.  Cursor authenticates via ~agent login~ (or export
  ~CURSOR_API_KEY~ / ~CURSOR_AUTH_TOKEN~), and Copilot also honours

  ~$DSH_HOME/.credentials.yaml~ (its official DeepSeek route falls back to
  ~DEEPSEEK_API_KEY~), and ~DSH_HOME~ plus OMP's ~OMP_PROFILE~ /

  one profile's state rather than the launch default.  Gemini CLI keeps its
  own login in its ~.gemini~ home directory (sign in with a Google account
  once outside Emacs); the documented headless key passes through when

  route, and only one of them, because a set key disables Application
  Default Credentials.  Devin authenticates via ~devin auth login~ once
  outside Emacs, or export ~WINDSURF_API_KEY~ for headless use;
  ~DEVIN_MODEL~ optionally names its default model.

* Install

Not on an ELPA archive yet, so use one of the local routes.

#+begin_src elisp
(add-to-list 'load-path "~/agent-org")
(require 'agent-org)
#+end_src

* Quickstart

1. M-x ~agent-org-start~ RET ~goose~ RET — or skip the prompt with the
   per-provider command M-x ~agent-org-goose-start-agent~ (one per
   registered provider, the way ~agent-shell-<provider>-start-agent~
   works).  What happens next is
   [[*Starting: which session you get][~agent-org-session-strategy~]]: by
   default the chat you last had in this directory is reopened, without
   asking (~C-u~ offers the chooser instead).
   Opens =~Goose:myproj= and shows ~Goose ➤ Starting~ in
   the header line.  When the ACP ~initialize~ + ~session/new~
   handshake completes, the header fills in with everything the agent
   reported, and the buffer renames itself to the session it holds —
   =~Qoder:myproj [20260924_4]=: the agent, the project it
   is a chat of, plus the id, so three chats from one agent are three
   readable names in ~C-x b~.  The session's /title/ is deliberately not in the
   name — it is ~#+TITLE:~ at the top of the chat and of its transcript, where an
   agent that renames the session later (qoder does, after the first turn) can
   update it without the buffer's name moving under you.  The
   header line is the agent's own report of the session:
   #+begin_example
   Goose ➤ free ➤ auto ➤ agent-org ➤ ▁ 5k/128k ➤ Ready
   #+end_example
   (provider ➤ model ➤ mode ➤ project ➤ context usage ➤ status)
   The session id is not on the bar — it lives in the buffer body as a
   ~:ID:~ property in the top ~:PROPERTIES:~ drawer, readable and
   selectable like any text.
   The model segment is the /name/ the agent advertises ("MiniMax M3"),
   not the id it takes on the wire (~minimax/MiniMax-M3~); an agent that
   reports a current model without naming it falls back to the id, since
   a bar with no model reads as a bar with no model.
   The mode segment is the same kind of /name/: Qoder's permission mode
   shows as ~Bypass Permissions~, not the wire word ~yolo~ behind it, and
   it follows you mid-session when the agent reports a mode change.
   Scroll down into a long answer and the bar gains a /second/ row: the
   heading of the exchange you are reading, pinned there so the question
   stays on screen while its answer runs off the bottom.
   #+begin_example
   Goose ➤ free ➤ auto ➤ agent-org ➤ ▁ 5k/128k ➤ Streaming
   * RESPONDED Write a parser for the queue region, then test it against
   #+end_example
   It is one line, truncated with ~…~ at the window's width, and it
   disappears as soon as the real heading is back on screen — the pin is
   a reminder, never a duplicate.  [[*Configuration][~agent-org-sticky-heading~]]
   turns it off.  A part of an answer — a ~**~ line like ~ONGOING~, ~COMPLETE~
   or ~FAILED~ — is deliberately not pinned: that word changes every few
   seconds while the agent works, the prompt does not.
   Note: the first ~session/new~ can take tens of seconds while goose
   loads its extensions — the buffer stays on "Starting" meanwhile.
2. Type in the live =~* PROMPT=~ box at the end of the buffer — no
   unlocking, no composing step.  Once the session is Ready the box
   appears and never goes away: the heading itself is frozen, the body
   under it is always typeable, mid-turn included (that is where
   type-ahead goes).  Hit ~C-c a s~ to send; the draft becomes its own
   exchange — /the heading is what you typed/ — and the same empty box stays
   open for the next message.  Everything the program writes (headings,
   agent output, tool calls) is read-only via text properties, and turns
   render /above/ the box, so chat history can't be mangled by accident
   and a streaming reply never scribbles over what you are typing.  The
   cursor still travels freely over history — you can browse and copy
   it; typing into frozen text is refused.
3. Watch the reply stream into the exchange's quote block — under a
   ~#+ATTR_TEXINFO: :author~ line naming the model that answered it
   (~#+ATTR_TEXINFO: :author MiniMax M3~), so the pair reads
   ~* <your prompt>~ / that model said this, with no ~* Agent~ heading to
   wade through:
   #+begin_example
   * Refactor the auth module

    and keep the tests green

   #+ATTR_TEXINFO: :author MiniMax M3
   #+begin_quote
    The parser is *line* based:

    - one rule per line
   #+end_quote
   #+end_example
   Every tool call is
   one ~  - KEYWORD title~ item of the turn's ~:tool:~ drawer (~TODO~ pending →
   ~ONGOING~ running → ~COMPLETE~
   done / ~FAILED~ failed), redrawn in place as the state changes,
   and what the call printed appears under its own item, indented four
   columns.  The ~:tool:~ drawer is *expanded by default* and stays
   expanded while the turn is running — a board that collapsed would hide the
   agent's next action — and ~TAB~ on the turn folds calls and output together
   once it has stopped (nothing is ever truncated, and a call that printed
   nothing gets no body lines), while extended thinking accumulates in one
   folded ~:thinking:~ drawer below the quote.
   Sending while the agent is still responding /queues/ the draft
   (~agent-org-queue-when-busy~, on by default — agent-shell's type-ahead
   model): queued prompts go out FIFO as each turn ends successfully.
   What is waiting is shown /in the chat/, at the bottom: each waiting
   prompt is a heading above the live ~* PROMPT~ box — the first says
   ~* NEXT~ and every one behind it ~* WAIT~, because the word /is/ its
   position in the send order.  ~C-c a q~ (~agent-org-queue-edit~) takes you there; edit a
   prompt in place, ~C-c a a~ adds a blank one at the bottom to type into,
   ~C-c a d~ kills one, ~M-UP~ / ~M-DOWN~ re-order (the order in the region
   /is/ the send order), and ~M-x agent-org-queue-apply~ (~agent-org-queue-apply~)
   is what puts the result on the wire.  Nothing is sent until you apply:
   a queue you are rearranging must not change under your hands, and the
   same list is mirrored into the transcript as these headings, so quitting
   Emacs mid-turn does not swallow a prompt (see [[#transcript-file][Transcript file]]).
   Three verbs need no position in the buffer at all, because a queue you
   cannot see is a queue you cannot trust: ~C-c a e~
   (~agent-org-queue-enqueue~) queues a prompt typed in the minibuffer while
   your cursor stays wherever it is, ~C-c a v~ (~agent-org-queue-list~)
   numbers every waiting prompt in the echo area, and ~C-c a x~
   (~agent-org-queue-remove~) takes that number (or ~all~) and deletes the
   entry from the page /and/ the session list together.
   And a prompt that arrives while you are editing the region /shows up/
   anyway: your half-typed words are never rewritten, the newcomer is
   appended below them, so the header's ~N queued~ always matches the number
   of headings you can count.
   The same holds on the way /out/: when a turn ends and takes a queued
   prompt, that entry disappears from an edited region too — but only if it
   still says word-for-word what the package wrote there, so a prompt you
   re-worded is never reaped, and a queue that has just emptied leaves no
   region behind at all.
   ~C-c a r~ (~agent-org-queue-resume~) sends the next one now, which is
   the escape hatch after ~C-c a k~ cancelled the turn they were queued
   behind.

   ~C-c a l~ (~agent-org-lite-mode-toggle~) is the minimum-resources mode
   for one session (see the Resource monitor and lite mode section below).

If the agent asks for permission, the header line shows
~… ➤ Awaiting permission~ and the minibuffer lists the agent's own
option names (e.g. ~Allow once~, ~Reject once~) with ~Cancel~ last;
answering sends that option's id back, and Cancel --- or quitting the
prompt with ESC / ~C-g~ --- safely declines.

Killing the chat buffer stops its agent.  The ~qoder --acp~ (or ~goose acp~)
process belongs to ~acp~, not to the buffer, so ~kill-buffer~ alone would leave
it running and holding ~100 MB~ — agent-org calls ~acp-shutdown~ from its
kill-hook, which deletes the process and drops the session from the registry.

While that process is alive, ~kill-buffer~ asks first, in Emacs' own words —
~Process qoder --acp is running; kill it? ~ — exactly as it asks about a
~*shell*~ buffer.  Emacs would never notice on its own: ~acp~ starts the agent
with ~:noquery t~ and no buffer of its own, so the editor sees no process at
all.  Answering NO leaves the chat open and untouched.  The kills
agent-org makes on its own (backing out of a session chooser, opening a
session that is already live elsewhere, ~agent-org-reload~) never ask — a prompt
raised from inside an agent callback is a trap, not a question.

* Keys

Everything agent-org binds lives under ONE prefix, ~C-c a~, which ~org-mode-map~
leaves free --- and a chat buffer /IS/ an Org buffer, so a package key on an Org
chord is a stolen command, not a preference.  The package used to sit on ~C-c
C-g~, one of the two ~C-c C-<letter>~ slots Org leaves empty (the rest are
claimed: ~C-c C-c~ is ~org-ctrl-c-ctrl-c~, the only gesture Org offers for
refreshing a clocktable or editing a block, both of which a chat contains, and
~C-c C-m~ PARSES as ~C-c RET~, Org's own ~org-ctrl-c-ret~); ~C-c a~ is one
keystroke shorter.  A test measures the rule against a fully loaded
~org-mode-map~, so if Org ever claims ~C-c a~ too it fails there rather than in
your fingers.

| Keys              | Command                         | Effect                                      |
|-------------------+---------------------------------+---------------------------------------------|
| ~C-c a s~       | ~agent-org-send~                | send the typed prompt (queues it mid-turn)   |
| ~C-c a k~       | ~agent-org-cancel-turn~         | stop the running turn                        |
| ~C-c a i~       | ~agent-org-interrupt-and-send~  | stop the turn and send the box, in one go    |
| ~C-c a l~       | ~agent-org-lite-mode-toggle~    | cycle this session's lite scope (~C-u~: global) |
| ~C-c a m~       | ~agent-org-set-session-model~   | switch the session's model                   |
| ~C-c a c~       | ~agent-org-clock-display~       | show/hide the clocked total on each heading   |
| ~C-c a q~       | ~agent-org-queue-edit~          | go to the prompts waiting in this session     |
| ~C-c a Q~       | ~agent-org-queue-restore~       | repaint the region from the session's queue   |
| ~C-c a r~       | ~agent-org-queue-resume~        | send the next waiting prompt now             |
| ~C-c a a~       | ~agent-org-buffer-queue-add~    | add a queued prompt at the bottom            |
| ~C-c a d~       | ~agent-org-buffer-queue-kill~   | kill the queued prompt at point              |
| ~C-c a e~       | ~agent-org-queue-enqueue~       | queue a prompt from the minibuffer           |
| ~C-c a n~       | ~agent-org-queue-prepend~       | queue one as the NEXT out, ahead of the rest  |
| ~C-c a x~       | ~agent-org-queue-remove~        | remove one waiting prompt by number (or all) |
| ~C-c a v~       | ~agent-org-queue-list~          | list the waiting prompts, numbered           |
| ~M-UP~ / ~M-DOWN~ | ~agent-org-buffer-queue-move-up~ / ~-down~ | re-order the entry at point          |
| ~C-c a g~       | ~agent-org-resource-refresh~    | in the resource monitor: redraw the tables   |
| ~q~               | ~quit-window~                   | in the resource monitor: close it            |

The exceptions are deliberate and few: ~M-RET~, ~M-LEFT~ / ~M-RIGHT~,
~S-UP~ / ~S-DOWN~, ~C-c C-t~ and ~C-c -~ are bound to an error in a chat, ON
PURPOSE --- Org's structure commands on those keys write through the
~read-only~ text properties, so one of them fired mid-stream would corrupt the
exchange the agent is still writing.  ~M-UP~ / ~M-DOWN~ are taken over for a
positive reason: Org uses them to move a subtree, and in a chat the subtree
worth moving is the queued prompt under point.  Folding stays available the Org
way (~TAB~, ~S-TAB~), because folding only changes visibility.

* Starting: which session you get

~agent-org-session-strategy~ decides what happens between the handshake
and the session opening — the same three choices ~agent-shell~ offers:

| Strategy     | What ~M-x agent-org-start~ does                        |
|--------------+--------------------------------------------------------|
| ~latest~       | loads the most recently updated session, without asking |
| ~prompt~       | asks the agent what this directory already holds, offers it |
| ~new~          | opens a blank session, no listing round trip            |

~latest~ is the default: the chat you were just in is the one you are
almost always after, and a question with an answer you give the same way
every time is not worth a keystroke.

One call can pick a strategy without touching the setting, and the
prefixes are ordered by how much of the decision they hand back: ~C-u M-x~
forces ~prompt~ (the chooser, which is what the default used to be), ~C-u
C-u M-x~ forces ~new~ — the fast path that never asks the agent to
list.  ~latest~ means /modified/: the agent's ~updatedAt~,
or ~createdAt~ for a session nobody ever came back to, not the order the
agent happened to list them in.

~prompt~ is what ~C-u M-x agent-org-start~ reaches.  The offer is the agent's own
~session/list~ for
~default-directory~, newest first, each candidate labelled

#+begin_example
Investigate the 3-minute lag between Qoder's reply and the… (open)  Sep 28, 10:22  [c550e3a1]
Reconcile the failing ERT suite                                     Today, 09:14   [0f2c8e1a]
#+end_example

— the agent's title, when it last spoke, and the id that actually
selects it.  The columns line up however long a title is, and the date
and id are dimmed, so the list is scannable at a glance rather than
read line by line.  ~New session~ sits at the top of the list, and the
order is pinned so it stays there, so a bare ~RET~ in a fresh project
still means "start".  A chat that is already open in another window is
marked ~(open)~: choosing it shows that window instead of loading the
same session a second time.  Backing out of the offer (ESC /
~C-g~) closes the half-open chat buffer and its agent, instead of leaving a
window stuck on "Starting".  ~C-u C-u M-x agent-org-start~ forces
~new~ for one call, which is the shortcut when you mean to start over.

Three details make this bearable on agents that are slow, silent or long:

- The listing follows the agent's ~nextCursor~, so chats older than the
  first page are offered too.  ~agent-org-session-list-page-limit~ caps
  the requests; nil, the default, reads every page.  Each page ticks a
  line in the echo area — ~Listing sessions... 38 so far~ — so a
  directory with hundreds of chats reads as work in progress, not as a
  hang.
- goose advertises ~list~ and never answers it, so
  ~agent-org-session-list-timeout~ gives up and opens a new session
  instead, saying so in the echo area /and/ on the header line — the
  status reads ~Ready (new session: listing timed out after 20s)~ rather
  than plain ~Ready~, so a fallback never looks like a prompt that failed
  to appear.  Starting a chat is never blocked by the feature that shows
  you the older ones.  On goose that wait is wasted every time, and the
  default now pays it before opening anything, so
  ~M-x agent-org-goose-start-agent~ followed by ~C-u C-u~ — or
  ~agent-org-session-strategy~ set to ~new~ — is the quick path.
- An agent that cannot list or cannot ~session/load~ is asked neither:
  the capability check happens on the ~initialize~ response, so it costs
  nothing.

* Resume a session

~M-x agent-org-resume-session~ reopens a session the agent still remembers for
the *current directory*, with its whole history replayed into a fresh
Org buffer:

| Keys              | Effect                                                     |
|-------------------|------------------------------------------------------------|
| ~M-x~ (no prefix)   | provider = ~agent-org-default-provider~, pick from the list |
| ~C-u M-x~           | prompts for the provider first                              |
| ~C-u C-u M-x~       | prompts for a session id directly, skipping the listing     |

The listing comes from the agent's own ~session/list~ for
~default-directory~ of the buffer you call it from — open the
project you want to resume in, first.  It is the same request
~agent-org-start~ makes, including the walk over ~nextCursor~ pages, so
an agent holding 38 sessions in this directory offers all 38, not the
first page.  One candidate is used without prompting; the header line
shows ~Restoring~ while the history is replayed, then ~Ready~ with a
live ~* PROMPT~ prompt at the end, and you continue exactly where you
left off — including prompts you had queued but never sent, which come
back from the queue region at the bottom of the transcript and go out in
order (the agent's own replay cannot contain them, because it never saw
them).

Resume is cheap on purpose (this is a 4 GB machine): the replayed
~session/update~ notifications are buffered while the load is in
flight and painted in one pass with undo recording off, so a long
history costs one insertion run instead of a full redraw per chunk.
Org colours are never switched off for that pass — a buffer that is
not on screen cannot have them put back, so suppressing them to save
time is how a resumed chat lost them for good.
The echo area reports both halves: a spinner while the updates
arrive (~Restoring session history... |~) and then a percentage for the
single paint pass, because that pass is the one that knows how many
turns there are (~Restoring session history...42%~).  Nothing runs on a
timer — the events themselves are the clock — so a quiet agent costs
nothing, and ~agent-org-progress-min-time~ bounds how often the line is
redrawn (raise it to 0.5 or 1.0 if the machine is straining).

goose advertises ~session/list~ and never answers it.  Resume therefore
sits on ~Restoring~ until you cancel with ~C-g~ — it will not guess a
session for you — which is why ~agent-org-default-provider~ is qoder, and
why ~agent-org-start~ has a timeout where resume has none (starting must
not be blocked by the listing; resuming is one you asked for).

* Switching between open chats

~M-x agent-org-switch-buffer~ lists the chats that have a live buffer right
now, in the order you opened them (newest first), and switches to the one you
pick.  Each row is ~LABEL  STATUS  [id]~, with the columns padded to the
widest row in the batch, so you scan down the state column instead of reading
six names that differ in the middle.  Verbatim from a real session:

#+begin_example
Qoder:sane-packages          Streaming  [7f9e546b-8f42-4c03-87af-3f019e31a70e]
Qoder:org-import             Ready      [3dfe858f-a84b-4f09-ab2c-3a3f29198fdb]
Qoder:agent-org              Streaming  [b480ebca-6b06-467e-822a-88cf491b75fa]

The label is ~<agent>:<project>~ for the reason those rows show: two ~Qoder~
chats in two checkouts are otherwise identical but for a UUID, and the id is
what separates two chats of one agent in one project.  What the chat is /about/
is not in the label either — that is the ~#+TITLE:~ inside it, and the topic an
agent renames later would otherwise rename the buffer mid-read.
~STATUS~ is the header line's own word (~Ready~, ~Streaming~, ~Restoring~…),
and ~C-x b~ says the same thing, because a chat has one display name wherever
it is listed.  There is no key binding: ~C-x b~ already reaches every chat,
and this is the short list of the ones with an agent behind them.

* Resource monitor and lite mode

A machine running agents is a machine under load: every chat holds an agent
process of its own (~100 MB for ~qoder --acp~, measured), and a long chat
holds a large buffer.  Two commands are about that, and neither of them costs
anything when you do not use them.

~M-x agent-org-resource-monitor~ opens ~*agent-org resources*~: an Org
buffer of tables, one row per open session, plus a machine row.  Each row
carries the session's label, its state, its lite scope, the agent's process,
its CPU since the last refresh, the agent's resident memory, the chat's
characters, and the transcript's size on disk.

| Emacs | Agents | Agent RSS | Sessions | Load 1/5/15 |

| Session | State | Mode | Agent | CPU | RSS | Buffer | Transcript |

~C-c a g~ redraws it, ~q~ closes it, and a prefix argument
(~agent-org-resource-monitor~ with ~C-u~) narrows it to the session you call
it from --- the reading you want when you suspect one chat.  It refreshes
itself every ~agent-org-resource-refresh-interval~ seconds (5) *while it is
on display*, and stops the moment you leave the buffer: it is the only
repeating timer this package runs, and it exists to report load rather than
add to it.  Everything is read from ~/proc~, so the numbers are the kernel's.

~C-c a l~ cycles one session's /lite/ scope:
=inherit= (the default) follows the global setting, =on= and =off= pin this
session against it, and ~C-u C-c a l~ flips the global
(~agent-org-lite-mode~) for every session that does not have a scope of its
own.  Lite mode spends nothing on machinery nobody is reading:

- no transcript write — /except/ while a prompt is queued, because a queued
  prompt exists in no replay and no agent memory (see
  [[#transcript-file][Transcript file]]);
- no undo records, so the chat's buffer is not shadowed by an undo list
  for a text nobody edits;
- no whole-buffer Org reparse on every metadata rebuild, which is what a
  long chat pays for a ~#+TODO:~ line that never changes.

What it does not do is turn off colours, drop the agent's reasoning, or stop
converting Markdown to Org: those are the conversation, not the machinery.

** Clocked seconds in the headings

Every exchange is clocked: the property drawer under its heading carries
=:RESPONSE:=, the exact whole seconds from the prompt going out to the answer
finishing, and a ~:LOGBOOK:~ ~CLOCK:~ range in Org's own shape sits beside it.
While the answer is still streaming, that range has no end yet and the property
reads ~0~ — which is what the heading shows, ~[0:00:00]~, rather than a number
guessed from a turn that has not finished.

Org cannot show you those seconds.  Its clock arithmetic works in whole minutes
(~org-clock-sum~ over a 45-second answer is ~0~, and ~0:00~ is what reaches the
screen), and a ~CLOCK:~ line that /carries/ seconds is not a clock line at all —
Org's parser reads zero clocks from it, which would hide your exchanges from
~org-clock-sum~, from a clocktable and from ~org-clock-load~ while still looking
right to the eye.

So ~M-x agent-org-clock-display~ (~C-c a c~) is a fork of ~org-clock-display~
that reads our number instead of Org's arithmetic: each heading with a timing
gets a dim ~ [H:MM:SS]~ at its line end, and the echo area reports how many
headings were counted and the total.  It is /on by default in a chat/
(~agent-org-clock-display-default~), and ~C-u C-c a c~ turns it off — the
gesture you press when the totals are noise is never the one that adds them.

- The totals are overlays, so nothing is inserted: the transcript file, the
  queue and every redraw read the buffer's bytes, and those bytes do not change.
- The total adds up the exchange headings only.  A part's seconds are already
  inside its exchange, so counting both would bill the same time twice — each
  part heading still shows its own number.
- A clock /you/ filed with ~C-x C-n~ / ~org-clock-out~ shows up too, at whatever
  precision its stamps carry; a clock still running is left alone, because it is
  yours and its end is not ours to invent.
- A /lite/ session skips the refresh (§19 of CONVENTIONS.md), so the numbers do
  not come back until the next turn boundary after lite is switched off.

** Seeing the raw wire

~M-x agent-org-show-traffic~ in a chat buffer opens acp's own traffic log for
that session's process: one line per message — time, direction, kind, method —
with ~RET~ pretty-printing the whole JSON object under the cursor, ~n~ and ~p~
stepping between messages, and ~C-x C-s~ writing the log as Lisp data (which is
how a test fixture gets a real agent's shape).  It holds every request we sent
and every response and notification that came back, /including the ones
agent-org never reads/.  That is the point: the chat body, the header line and
the drawers are each a rendering of a chosen subset, so "what did the agent
actually answer?" — and any disagreement between its answer and what the buffer
recorded — is settled only by the bytes on the wire.  A chat whose agent is not
running has nothing to log, and says so in the echo area.

* MiniMax Code

MiniMax Code is its own terminal coding agent: ~mcode~, whose ~mcode acp~
subcommand "runs MiniMax Code as an Agent Client Protocol server over
stdio".  It is a /different product/ from OpenCode, which is a host that
fronts many vendors' catalogues, MiniMax's models among them.  So the
~minimax~ provider spawns ~mcode acp~ and pins nothing: MiniMax Code's
default model is already a MiniMax model (here ~defaultModel:
minimax/MiniMax-M3~ in ~.minimax/config.yaml~), and overriding it would
only fight the CLI's own configuration.

#+begin_example
M-x agent-org-minimax-start-agent
#+end_example

Sign in once outside Emacs — ~mcode login~ (there is also
~mcode acp login~) — and the session needs no environment variable.

* Switching models on an agent that fronts many

One ACP server can serve many models, so a provider plist /may/ carry
~:model~ (see ~agent-org-providers~).  Once the session is Ready,
agent-org sends ~session/set_config_option~ for that id and the header
line's model segment shows the model you are actually on — ~M-x
agent-org-opencode-start-agent~ then picking a MiniMax id is how you run
MiniMax /through/ OpenCode, which is not the same thing as MiniMax Code.
Both the chooser and the header show the agent's own label
("OpenCode Zen/MiniMax-M2.7"); the id stays behind, which is why ~C-c
C-g m~ can be read without knowing a catalog's naming scheme.

| Keys                      | Effect                                          |
|---------------------------|-------------------------------------------------|
| ~C-c a m~               | complete over the models this agent advertises   |
| ~M-x agent-org-set-session-model~ | same, from lisp or ~M-x~                         |

Only ids the agent listed are accepted — OpenCode renames its catalog
between releases, so a stale pin is reported in the echo area instead of
sent and failed, and the session keeps working on whatever model the
agent chose.  Live OpenCode 1.18.29 advertised 158 values including
~opencode/minimax-m2.5~, ~opencode/minimax-m2.7~ and
~opencode/minimax-m3~; ~M-x agent-org-set-session-model~ is how you see the
current list.

OpenCode is a Bun binary that boots slowly on a weak machine — expect
"Starting" for a good while before the handshake answers (measured here:
Ready at 31–65s).  It is starting, not stuck.

MiniMax through OpenCode Zen is metered, so a prompt can come back as
~prompt failed: Upstream request failed: Insufficient account funds~ in
the header line.  That is the upstream account talking, not a broken
session: the id, the mode and the model are all still there, and topping
up only needs a fresh ~C-c a s~.

* What the agent is told about this connection

Ask an agent "which model are you?" and it answers from its own idea of
the default.  That is wrong the moment you switched with ~C-c a m~ — which
is the normal case for MiniMax running /through/ OpenCode — and the
session id and the harness name are facts of the same kind: the client
knows them, the agent cannot derive them, and a commit trailer or a bug
report wants them.  So every prompt carries a second text block:

#+begin_example
<agent-org-context>
Client metadata about this connection, not part of the user's request.
agent: Qoder (qoder)
model: MiniMax M3 (minimax/MiniMax-M3)
session: 7c1f-abc
</agent-org-context>
#+end_example

Both spellings of each fact go, because they answer different questions:
the label is what a person reads and an agent quotes, the id is what a
commit trailer, a bug report or a ~session/set_config_option~ request
needs, and neither one derives from the other.  An agent that advertises
no model of this shape (goose) simply gets no ~model:~ line — a
~model: nil~ line would be an agent told something false.

The block is rebuilt every turn, so it follows a mid-session ~C-c a m~,
and a prompt that waited its turn in the queue carries the same facts as
one you typed.  Your own text is untouched and stays the first block: the
agent receives the question verbatim, and the client speaks beside it
rather than inside it.  ~agent-org-send-session-context~ nil sends only
what you typed.

Verified live on qoder: asked to read the block and print its fact lines
back, an agent answered ~agent: Qoder (qoder)~,
~model: Qwen3.8-Flash (qfmodel)~ and the session id it had never been
told by anything else, and named the block as the client's rather than
yours — which is the delimiters doing their job.

* Session metadata
:PROPERTIES:
:CUSTOM_ID: session-metadata
:END:

At the top of every chat buffer, above the first conversation
heading, ~agent-org~ keeps a frozen Org-native metadata section that
refreshes itself as the session reports new facts:

- a ~:PROPERTIES:~ drawer at the very top, before everything else,
  carrying the scalars (Provider, ID — the ACP session id, only once
  the agent has issued one, Mode, Model, Context, Cost, Tokens),
- a ~#+TITLE:~ keyword line (provider — session title),
- ~:COMMANDS:~ (available ~/slash-commands~), ~:MODES:~ and
  ~:CONFIG:~ drawers listing everything the agent advertised.

No heading is used — ~* ~ lines belong to the conversation, and to the
/queue/, which is a region of ~* TODO~ headings at the bottom of the chat
rather than a drawer of this block.  The reference drawers start folded, so
the block is a few marker lines, and ~TAB~ on a drawer line opens or closes
it.  The block is deleted and re-inserted on every update, so it never
duplicates and never disturbs the conversation below it.

* Transcript file
:PROPERTIES:
:CUSTOM_ID: transcript-file
:END:

By default every session also has an Org file of its own, in
~.agent-org/~ *inside the project the chat is of*
(~agent-org-transcript-dir~; set an absolute path there for one
global pool), named for its ACP session id: ~7c1f….org~.  The file is a mirror of the
chat buffer — the same headings, the same tool-call keywords, the same
~:PROPERTIES:~ drawer, whose ~:ID:~ is the id in the file name, so a
transcript is an ~id:~-linkable document you can reference from any org
file.

It is written at turn boundaries (when a prompt goes out, when the turn
ends, when a session is restored, and once more when the buffer is
killed) and whenever the prompt queue changes, never per chunk: a
twenty-chunk answer costs two whole-file
writes, so a slow disk cannot stall a stream.  Measured on this machine
(a spinning disk, 4 GB RAM), one boundary write is ~3 ms~ for a short
chat, ~6 ms~ at 20 turns (~21 KB~), ~15 ms~ at 100 turns (~407 KB~);
the identical body is skipped in under ~0.1 ms~.  agent-shell's per-chunk
append, which is what this replaced, costs ~90-170 ms~ for the same 20
turns — and spends it inside the stream.

Mirroring rather than appending is also why the file is never wrong about
a tool call: a ~:tool:~ item that moved TODO→ONGOING→COMPLETE in the buffer moves it
in the file too, where an append log would keep three items for one call.
A draft still in the =~* PROMPT=~ box never reaches the file, and a failed
write is a note in the echo area, never a broken turn.

One thing in the file is /not/ conversation: prompts you sent into a busy
session, which are waiting their turn.  They have no heading yet, and the
agent has never seen them, so its own history cannot give them back on a
resume.  They are recorded in the transcript as the chat's own queue
region: ~* TODO~ headings under two ~;;~ preamble lines, /re-rendered/ from
the session's list by ~agent-org-buffer-transcribe~ rather than copied out
of the buffer — the region is the user's text and may be half-edited.
~agent-org-resume-session~ reads them back through the same parser,
reloading them and sending the first, the way the end of a turn would have.
The preamble is what finds the block — the LAST such block, since it is
always the final thing in the file — and an empty queue writes no block at
all, which is what stops a prompt being sent twice.

In lite mode this is the ONE write lite mode does not skip: see
the Resource monitor and lite mode section.

Because the file is refreshed only at boundaries, a chat you have left idle
since an upgrade keeps the shape it was written in, even though the running
buffer now renders newer features.  ~M-x agent-org-transcript-sync~ catches the
file up /now/, with no new prompt: it rebuilds the metadata block and rewrites
the whole mirror even when the text looks unchanged and even in lite mode.  With
a prefix arg (~C-u M-x agent-org-transcript-sync~) it does every open chat at
once.  It re-/mirrors/ the buffer; it does not re-/render/ an old conversation,
so to rebuild an old chat body from the wire, ~agent-org-resume-session~ it
first (that replays and repaints every turn) and then sync.  With
~agent-org-transcribe~ nil there is nothing to sync, and the command says so
rather than writing a file you turned off.

Turn it off with ~agent-org-transcribe~ nil — a chat whose transcript is
a real org file under version control does not want a second copy
appearing behind it.  A project that has no use for the files can add
~/.agent-org/~ to its ~.gitignore~; this repo does.

* What the agent wrote becomes Org

Agents answer in Markdown, and this buffer is Org, where the two syntaxes
disagree /structurally/: a ~#~ heading at column 0 is an Org comment (it
disappears from every export), a ~*~ bullet is a level-1 headline (it cuts the
turn in two / and ends the answer's quote block), and a line of dashes under a
paragraph is a headline too.  So a
reply's text — and your own echoed prompt — is rewritten on the way in
(~agent-org-convert-markdown~, default on):

#+begin_example
  # Heading     *Heading*       bold: a headline would end the quote
  * item        - item
  **bold**      *bold*          one marker, not two
  *italic*      /italic/
  `code`        =code=
  [t](URL)      [[URL][t]]
  ---            ---            one space of indent
  ``` sh        #+begin_src sh
  |:--|--:|     |---+---|       Org's column groups
#+end_example

- A Markdown heading becomes BOLD, not an Org heading: the answer lives inside a
  quote block and a headline of /any/ level ends one, so ~## Summary~ that kept
  its size would cut the reply out of its own block.  The words survive, the
  size is what is given up.
- A fence becomes a real source block and its body is left alone — a shell
  sample full of ~#~ and ~*~ is code, not markup.  A fence the agent never
  closed is closed for it, because an open one hides the rest of the buffer
  and the rest of the transcript file.
- A table's separator row gains Org's column groups, which is what keeps a
  header row a header: the alignment-colon form is not Org's separator, so
  with it the header is lost and the alignment markers export as dashes.

Numbered lists and ~- [ ]~ checkboxes already mean the same thing in both
syntaxes, so no rule touches them; neither does anything touch a ~_word_~,
whose Org reading needs non-word characters around it and whose rewrite would
eat ~foo_bar_baz~, or a strikethrough, which is only cosmetic.  The rewrite
runs while the reply streams: every chunk is written at once and only the
last, still-arriving line is rewritten by the next chunk, so a construct
split across two chunks reaches the buffer once, as markup, instead of first
as stars.

What the /agent/ receives is unchanged — your Markdown goes out exactly as you
typed it — so this is rendering, not translation.  Set
~agent-org-convert-markdown~ to nil to get the agent's bytes verbatim, which is
what this package did before the option existed.

* Configuration

- ~agent-org-use-header-line~ — when nil, status messages go to the
  echo area via ~message~ instead of the top bar.
- ~agent-org-sticky-heading~ — when non-nil (the default) the top bar gains a
  second row holding the prompt of the exchange you have scrolled into, one line,
  truncated to the window: see [[*Quickstart]].  Nil pins nothing, and clears
  a pin already showing rather than waiting for the next chat.
- ~agent-org-quote-model-author~ — when non-nil (the default) an answer's quote
  block is attributed to the model that wrote it
  (~#+ATTR_TEXINFO: :author MiniMax M3~).  Nil keeps the stable word
  ~:author Agent~, for a transcript kept across a provider switch where a model
  name in the notes would be a claim about someone else's catalog; an agent that
  advertises no model gets ~Agent~ either way.
- ~agent-org-convert-markdown~ — when non-nil (the default) Markdown in a
  reply, and in your own echoed prompt, becomes real Org markup: see
  [[*What the agent wrote becomes Org]].  Nil leaves the agent's bytes verbatim.
- ~agent-org-send-session-context~ — when non-nil (the default) every prompt
  carries a second text block with the agent's name, the selected model and
  the session id: see [[*What the agent is told about this connection]].
  Nil sends only what you typed.
- ~agent-org-default-provider~ — provider ~agent-org-resume-session~ uses when
  you call it with no prefix argument (qoder by default: it answers
  ~session/list~, goose does not).
- ~agent-org-transcribe~ — when non-nil (the default) each session is mirrored
  to its own Org file, see [[*Transcript file]].
- ~agent-org-transcript-dir~ — where those files live.  The default
  is the relative ~.agent-org~, resolved against the chat's own directory,
  so every project keeps its own transcripts; an absolute value is a global
  pool.  Created on the first write.
- ~agent-org-session-strategy~ — what starting means: ~new~, ~latest~ (the
  default) or ~prompt~, see [[*Starting: which session you get]].
- ~agent-org-session-list-page-limit~ — how many ~session/list~ pages to
  follow; nil reads every page.
- ~agent-org-session-list-timeout~ — seconds ~agent-org-start~ waits for
  the listing before opening a new session instead; nil waits forever.
- ~agent-org-replay-settle-delay~ / ~agent-org-replay-settle-cap~ — how
  long a resume waits for the agent to stop streaming history before it
  paints it, and the hard upper bound on that wait.
- ~agent-org-lite-mode~ — when non-nil, every chat runs in lite mode; a
  session with its own scope overrides it.  See
  the Resource monitor and lite mode section.
- ~agent-org-resource-refresh-interval~ — seconds between refreshes of the
  resource monitor, and only while it is displayed; nil or 0 turns
  auto-refresh off and ~C-c a g~ in the monitor redraws on demand.
- ~agent-org-clock-ticks-per-second~ — Linux ~USER_HZ~, which is what the
  monitor's CPU column divides by.  100 everywhere it was measured.
- ~agent-org-progress-min-time~ — seconds between redraws of the loading
  line in the echo area (0.2, Emacs's own default).  Raise it to 0.5 or
  1.0 on a machine that is struggling; the line then updates less often
  while the work itself is untouched.
- ~agent-org-providers~ — list of provider plists (~:id~, ~:name~,
  ~:command~ (binary + args), ~:environment~, optional ~:model~ to pin
  for every session of that provider).  Add more agents by customizing
  it or pushing onto it in your init.
