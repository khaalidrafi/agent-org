* How to use this file

Every unit of AI-written code that is hard to review or easy to get wrong gets a
TODO here, with the file, the function and the one question to answer.  Done
means you read the code and agree it is right, not that the tests passed.

* Starting with the directory's older sessions (=agent-org-session-strategy=)

** TODO Read =agent-org-start= and =agent-org--begin-start= (agent-org.el)

The strategy is read once, in the command, and then travels with the session
through both callbacks that need it.  Question: agree that no callback should
ever read ~agent-org-session-strategy~ itself.  This was found live, not
theoretical: a probe that wrapped ~agent-org-start~ in
~(let ((agent-org-session-strategy 'new)) ...)~ still sent ~session/list~,
because ~initialize~ answered after the ~let~ had exited and the callback read
the global value.  The same trap already governed ~current-prefix-arg~, which
is why ~agent-org-start~ captured ~forced~ early; the bug was that the strategy
was not treated the same way.

** TODO Read =agent-org--settle-listing= and the registry's =:list-state=

One listing, exactly one outcome: whoever settles first — answer, failure or
the timeout — acts, and whoever arrives after is ignored.  Without it a goose
that answered 30 s late would load a second session into a buffer that had
already opened a fresh one.  Question: is leaving the value at ~settled~ right
(never back to ~nil~), and do you agree that
~agent-org--resume-locate~ needs no such guard because it arms no timer?

** TODO Read =agent-org--list-sessions='s repeated-cursor branch

A cursor the agent hands back twice is a FAILURE, not another page.  Question:
should it instead stop paging and offer what was already fetched?  Failing was
chosen because a partial list that looks complete is worse than no list — the
user cannot tell a truncated listing from an empty directory.

** TODO Judge the =agent-org-session-list-timeout= default on your own agents

20 s is a judgement, not a measurement: cold listings on this machine answered

** TODO Read the ~:note~ rules (agent-org-buffer.el, agent-org-loader.el)

Three decisions to re-examine, all small and all easy to get wrong later:

- It renders for ~ready~ only.  ~starting~ ignores it, so the bootstrap stays a
  plain state label; the reason appears the moment there is a session to explain.
- It is cleared by ~agent-org-loader-begin~, not by ~agent-org-send~ — so the note
  survives the whole chat.  Right or wrong, that is the choice: "why is this
  session empty" stays answered, at the cost of a suffix nobody re-reads.
- Agent-supplied reasons go through ~agent-org-buffer--label~, so a long
  ~session/list~ error becomes one truncated clause.  Check the width
  (~agent-org-buffer--label-width~) actually suits a status bar.

* Cancelling the session prompt must not strand a buffer

** TODO Read =agent-org--quit-cancels= (agent-org.el)

~completing-read~ signals ~quit~ on ESC/~C-g~, and here it signals it /inside an
acp response callback/ — which acp runs under ~condition-case-unless-debug~, so
the quit is swallowed whole.  Nothing errored, nothing was logged: the chat
buffer simply stayed on "Starting" with a live ~qoder --acp~ process behind it.
The macro is three lines; the thing to judge is whether /kill/ is the right
reaction to a cancel (it is what agent-shell does when you back out of a
selection, and it is cheap now that ~kill-buffer~ releases the agent) versus
reusing the buffer for the next ~agent-org-start~.

** TODO Read the nil-is-cancelled contract (agent-org.el)

Both readers (~agent-org--read-start-choice~, ~agent-org--read-session-id~)
complete with ~REQUIRE-MATCH~, so a nil out of ~agent-org--quit-cancels~ can only

accept free input, or returns ~nil~ for "not found", a cancelled start would
silently become a ~session/load~ of nil.  A ~:cancelled~ sentinel is the fix if
that ever happens.

* A session list you can scan: padded columns, pinned order

** TODO Read =agent-org--session-candidates= as the whole pipeline
Three passes over the same rows exist for one reason: a column can only be
padded once you know the batch's widest value, so
=agent-org--session-columns= (values) → =agent-org--column-width=
(widths) → =agent-org--session-display= (painted row) cannot collapse
into one function.  Note what a reviewer should check: the widths are
computed once, outside the =seq-mapn= — hoisting =agent-org--column-width=
into the row lambda would make the whole function O(n²) on a 40-session
listing, which is exactly how it was first written and then fixed.
Every title is still flattened by =agent-org-buffer--label= twice (once
for measuring, once for the row); if that bothers you, pass the measured
=cols= through instead of re-deriving, which the =cols= argument already
allows.

** DONE Why the date and id are dimmed, and the title is not
=shadow= is the conventional de-emphasis in a completion list, and the
title is the only column a human reads.  Padding happens before
=propertize=, so the spaces belong to the dimmed column — which is why
the id is NOT padded: a padded tail would be trailing whitespace in the
candidate the UI echoes back into the minibuffer.

** DONE Columns are measured in display width, not characters
=agent-org--pad= hand-rolls its padding.  =string-pad= looked like the
right primitive and is not: it counts characters, so a ten-character
Japanese title padded to a 31-character column occupied 41 columns on
screen and its date landed a dozen early.  =agent-org--column-width=
measures with =string-width= so the measuring pass and the padding agree;
=test-agent-org-candidate-columns-align-by-display-width= is what would
fail if anyone swaps =agent-org--pad= back to =string-pad=.

** TODO =display-sort-function= is a claim about the UI, not a guarantee
=agent-org--completion-collection= hands =completing-read= a function
carrying =(metadata (display-sort-function . identity))=.  That is what
agent-shell does, and it is honoured by the built-in =completion--docompose=
paths, but a framework (vertico, marginalia, consult) is free to ignore
metadata it does not implement.  So this is "we no longer hand our order
away", not "the order is enforced" — the pinned test asserts what we
offer, not what a given UI shows.  Worth checking on your own completion
stack; =test-agent-org-prompt-collection-pins-our-order= is the one that
would need extending if you add a =completion-styles= requirement.

** TODO The lookup is property-free now; =assoc= would have been a silent bug
=agent-org--selection-value= compares =substring-no-properties= because
=assoc= uses =equal=, and =equal= on strings compares text properties.
The displays now carry =face=.  A completion UI that returns the
collection's own member would still have worked, so this bug would only
have appeared on the machine of whoever uses a framework that rebuilds the
string — and it would have resumed the WRONG session, not errored.  Read
it as the reason =agent-org--session-candidates= is allowed to return
propertized text at all.

* Choosing an already-open session switches instead of loading twice

** TODO Read =agent-org--load-session='s short-circuit (agent-org.el)
The guard sits at the top of =agent-org--load-session= rather than in
=agent-org--choose-start=, on purpose: every path that could load a
session id goes through it — =prompt=, =latest=,
=agent-org-resume-session= with no argument, and the double-prefix
=agent-org-resume-session= where the user TYPED the id.  Judge that: a
typed id is an explicit request, and silently being shown another
window instead is arguably the wrong answer for it.  The counter-argument
in the code is that a second client on one session id is not a supported
shape at all, so the explicit request cannot be honoured anyway.

** DONE The switch kills a buffer without asking
=agent-org--show-open-instead= kills the half-open buffer to release the
agent process it spawned (the only release path is the kill-hook), then
pops the target.  That kill is silent.  It destroys no conversation — the
buffer never got a session — but it does throw away whatever
=#+TITLE=/drawer block had been painted.  This is the same question the
kill-buffer TODO above asks; if you add a confirmation, add it to both
paths, not here alone.

RESOLVED the other way, deliberately: the confirmation went on the USER's
kill (=kill-buffer~, =C-x k~=), and every kill agent-org performs on its own
stays silent — =agent-org--show-open-instead=, =agent-org--cancel-open= and
=agent-org-reload= all call =agent-org--kill-buffer-silently=, which binds
=agent-org--inhibit-kill-query=.  They run inside acp response callbacks, where
a prompt is not a question but a second way for the gesture to fail (see
[[Cancelling the session prompt must not strand a buffer]] for why a callback
must never block on the user).  Judge whether =agent-org-reload= belongs in that
list: it is user-initiated, and while the agent is responding it has already
asked its own question (=Agent is responding.  Reload anyway?=) before the
silent kill — but when the turn is idle it kills and re-opens with no prompt at
all, which is arguably the one place a person would want to hear "an agent is
running behind this buffer".

** DONE =(open)= lives inside the title column, not after the id
Marking a row after the id would have broken "the id is always last
because it is what actually selects", and marking it as a fourth column
would need the measuring pass to know about a column that only exists for
some rows.  Appending it to the title text before
=agent-org--column-width= runs means the marker is measured like any other
character, so the dates stay in line whether or not a row is open.

** TODO =agent-org--session-open-p= trusts the registry's =:session-id= timing

though: two resumes of the same id within one replay settle delay.  Read
=agent-org--load-session= and =agent-org--finish-replay= together and

* Loading is reported in the echo area (=agent-org--progress-*=)

** TODO Read =agent-org--progress-start= / =-step= / =-stop= (agent-org.el)

Question: is one report per *session* (the =:progress= key) the right owner,
rather than one per buffer?

It is per session because one session owns one echo area: =-start= stops and
replaces whatever report was there, so a phase that leaked a line cannot leave
two owners stepping it.  While reading, check the other half of the contract —
every key any of the three functions =setf=s is installed by
=agent-org--open-session=, because =setf= on a =plist-get= of a *missing* key
silently does nothing and the report would then never be seen or cleared.

** TODO Check who closes each report

Three phases, three owners, and the point is that no caller has to remember:

| phase                       | started in                    | closed by                                    |
|-----------------------------+-------------------------------+----------------------------------------------|
| =session/list= paging       | =agent-org--list-sessions=    | its three terminal =cond= arms + its =:on-failure= |
| listing timeout             | (the pager's, still open)     | =agent-org--list-timeout= — the one exit the pager cannot reach |
| =session/load= replay       | =agent-org--load-session=     | =agent-org--render-replay=, =-cancel-replay=, =-forget-session= |

Read those six sites and answer: can any of them leave a line spinning?  The
kill path is the safety net (=agent-org--forget-session=), so a phase that only
closes on success is a bug you can only see by killing a buffer mid-load — which
is what =test-agent-org-killing-a-loading-buffer-clears-the-report= does.

** TODO Verify the stop-*before*-the-note ordering (=agent-org--list-timeout=)

=-stop= is =(message nil)=, which erases the echo area.  So it must run *before*
the timeout writes its explanation, or the fallback reason deletes itself.  One
line of code, easy to invert during a refactor, and inverting it is invisible
until you read it — hence a test, =test-agent-org-listing-reports-and-clears-before-the-prompt=.

** DONE Why no timer: the =agent-shell-active-message-show= difference

agent-shell animates its reporter with =(run-at-time 0 0.1 …)= — ten wakeups a
second, of which Emacs displays at most five (its own throttle is 0.2 s), and
which keep waking the machine while the agent says nothing at all.  Here the
events *are* the clock: a replay chunk, one page. =progress-reporter-update= is
documented to do nothing when the change is too small or too soon, so the cost
that actually needs bounding is the redisplay, and
=agent-org-progress-min-time= bounds it with Emacs's own default.  Reuse the
shape (a reporter, =(message nil)= on the way out), not the exit list
(agent-shell hides from five subscription sites; we own each phase end to end).

** TODO Confirm the percentage appears only where a denominator exists

Only =agent-org--render-replay= passes =:total=, and only its loop steps with a
computed number (=cl-incf= of =painted=).  Arriving updates step with *no*
value.  Question to answer: right call?

Yes, and the reason is the cost of the counter, not its meaning: nobody knows
how many chunks an agent means to replay, and counting them per chunk =length=s
a growing list once per chunk — quadratic, on the 200-turn session, on the one
machine that cannot afford it.  The listing count looks similar but is not: =all=
is a *vector* (=vconcat=), whose =length= is O(1), and it ticks once per page
rather than once per token.

=agent-org-loader.el= deliberately gets no reporter: =initialize= is one round

** DONE Ten tests, and the harness bug they exposed

=ao--capture-messages= records the formatted line, so a test can count the

* A chat buffer asks before it dies (=agent-org--kill-query=)

** TODO Read the reader: an acp client is an ALIST that looks like a plist

This is the bug the offline suite could not see.  =acp-make-client= returns
=(list (cons :process nil) (cons :command ...) ...)= (acp.el:90) and fills it
with =map-put!=, which for a list is the /alist/ operation — so the keys carry
colons and the container is a list, and it reads exactly like a keyword plist
until you try to read it as one.  =plist-get= walked it, matched nothing and
answered nil on a /Ready/ session with a live =goose acp= child sitting in the
client.  =map-elt= with the same keyword key returned
=#<process acp-client(goose)-1>=.  acp itself reads it that way
(=acp--client-started-p=, acp.el:108).

The reason it survived 156 green tests is the /mock/: =tests/acp-mock.el= used
to hand out =(list :mock-client N)= — a genuine flat plist, so the wrong reader
worked in the suite and failed in the only environment that matters.  It now
builds the dotted-pair shape, and a mutation check confirms the line holds: put
the =plist-get= reader back and three kill tests fail
(~…kill-of-chat-buffer-with-agent-asks~, ~…kill-query-wording-names-the-process~,
~…kill-query-yes-kills-and-releases-the-agent~); with =map-elt= the suite is
156/156.

Worth generalising, because it is the shape of a whole class of stub bugs: a mock
must mirror the dependency's /data shape/, not merely its key names, or the suite
is testing the stub.

** TODO Read who asks and who never does

The query is on =kill-buffer-query-functions= /buffer-locally/, installed beside
the kill-hook by =agent-org--register-session=, so a non-chat buffer is never
asked and the global hook stays untouched.  Three answers mean /yes/: no session
registered, no process, or a process that already exited (a crashed agent leaves
a dead buffer, and consent to kill that is friction).  Everything else that
kills — =agent-org--cancel-open=, =agent-org--show-open-instead=,
=agent-org-reload= — goes through =agent-org--kill-buffer-silently=, which binds
=agent-org--inhibit-kill-query=.  Judge that list, and in particular
=agent-org-reload=: it is user-initiated, and its kill is silent.

** DONE Read the wording: it is Emacs' own question

=Process %s is running; kill it? = is the string =kill-buffer= uses for a
=~*shell*~= or compile buffer, so a chat buffer now asks the same question about
the same kind of object.  Emacs never asks it here by itself: =acp= starts the
agent with ~:noquery t~ and no process buffer, so
=process-kill-buffer-query-function= has nothing to find.  The test pins the
wording with a regexp (including the escaped ~\\?~ — an unescaped ~=?~ is a
quantifier, and the assertion then matches things it should not) and asserts the
process /name/ appears, because an unnamed "a process is running" is not
actionable.
